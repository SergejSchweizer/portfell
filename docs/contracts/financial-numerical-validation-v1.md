# Financial Numerical Validation Contract v1

Status: mandatory quantitative QA contract for Portfell.

## Purpose

Regression equivalence proves that refactors preserve existing behavior, but it cannot prove that the preserved financial mathematics is correct. Portfell therefore requires an independent numerical-oracle gate before the Dash replacement can be accepted as production-ready.

This contract is deliberately independent of the browser implementation. It validates the analytical backend first and then requires the browser to render the exact validated backend artifacts without recomputation.

## Gate placement

The gate must be implemented no later than the Dash four-page parity QA stage and must be part of the complete merge-quality path before final clean-runtime and production acceptance.

The intended proof order is:

```text
frozen market inputs
      |
      v
independent numerical oracle
      |
      v
Portfell analytical backend
      |
      v
immutable analysis artifacts
      |
      v
Dash tables / KPIs / Plotly figures
```

A PASS therefore proves three separate properties:

1. the expected financial values are independently derived from frozen inputs;
2. Portfell backend outputs agree with those independently derived values;
3. the UI displays those validated outputs without silently recomputing or changing them.

## Independent-oracle rule

Expected values must not be generated by importing or calling the production function under test, its immediate helper, or a second copy of the same production implementation.

For every metric, the test fixture must either:

- derive the expected value directly from the mathematical definition using simple transparent test code; or
- compare against a frozen externally reviewed golden value whose derivation is stored with the fixture.

The oracle must be sufficiently simple that a reviewer can trace every expected value from the frozen input rows.

Regression snapshots alone are not an oracle.

## Frozen deterministic datasets

The suite must contain small human-auditable datasets with exact dates and adjusted-close values. At minimum it must include:

- a monotonically rising series;
- a monotonically falling series;
- a flat series;
- a series with at least one non-trivial peak-to-trough drawdown and recovery;
- two perfectly positively related return series;
- two perfectly negatively related return series where the metric is defined;
- two non-perfectly correlated series with a hand-checkable common calendar;
- a pair with non-overlapping or insufficient observations that must become unavailable rather than zero;
- at least three assets forming a positive-semidefinite covariance matrix suitable for portfolio tests;
- missing `adjusted_close` evidence that must fail/show unavailable according to the analytical contract;
- dividend and split evidence proving that adjusted-close returns are not double-counted or re-adjusted.

Fixture data must be frozen, versioned, deterministic, timezone-independent, and free of live-network dependencies.

## Univariate oracle coverage

The independent oracle must validate, whenever the metric is part of the active Portfell contract:

- simple periodic returns from adjusted close;
- cumulative/compounded return;
- annualized return using the production contract's exact annualization convention;
- arithmetic mean return where exposed;
- annualized volatility using the exact degrees-of-freedom convention;
- downside deviation and Sortino inputs where exposed;
- Sharpe inputs/ratio where exposed, including the exact risk-free-rate convention;
- maximum drawdown and the dates/indices that define the peak and trough where exposed;
- distribution/income yield where exposed, separately from price/total-return calculations;
- observation count and unavailable-state rules.

The test must explicitly distinguish simple return, log return, arithmetic annualization, geometric compounding, and annualized volatility. No convention may be inferred from a chart label.

## Bivariate oracle coverage

The independent oracle must validate, whenever exposed:

- exact common-calendar alignment;
- paired observation count;
- covariance with the production contract's exact normalization/degree-of-freedom convention;
- Pearson correlation;
- pair eligibility/minimum-observation logic;
- duplicate/full-listing identity behavior;
- unavailable covariance/correlation behavior.

Missing covariance or correlation must never be encoded as `0` merely to make a matrix or plot render.

## Multivariate oracle coverage

The independent oracle must validate the portfolio arithmetic separately from the optimizer implementation. At minimum:

- weights sum to the required total within the contract tolerance;
- portfolio periodic return equals the weighted asset-return aggregation specified by the contract;
- expected portfolio return equals the agreed return aggregation;
- portfolio variance equals `w^T Sigma w` for a frozen covariance matrix;
- portfolio volatility is the square root of the validated variance, with the exact annualization rule;
- risk contributions reconcile to total portfolio risk when risk-contribution artifacts are available;
- cumulative performance from the frozen OOS return path is reproduced exactly within numerical tolerance;
- maximum drawdown of the OOS portfolio path is independently reproduced;
- candidate OOS metrics used for ranking match the persisted artifacts;
- the selected winner is the candidate implied by the frozen objective/ranking rules;
- final weights and DecisionArtifact identify the same winner and actual method;
- Equal Weight is never accepted as a hidden fallback after an optimizer failure.

Optimizer optimality may additionally be checked against analytically solvable toy cases, but such checks do not replace the arithmetic/oracle tests above.

## Walk-forward and OOS leakage checks

The numerical gate must include at least one deterministic walk-forward fixture proving:

- every training calculation uses only observations available at or before the training cutoff;
- no future OOS observation contributes to feature/statistic/covariance estimation for an earlier fold;
- OOS candidate metrics are computed only from the designated OOS interval;
- changing a future observation cannot change an already completed earlier-fold result;
- fold aggregation and final winner ranking follow the frozen production contract rather than a fixture-only shortcut.

## Numerical tolerances

Every floating-point assertion must declare its tolerance and why that tolerance is appropriate.

Rules:

- exact integer/count/date/identity/status assertions use exact equality;
- Decimal/source values remain exact until the documented analytical projection boundary;
- deterministic algebra on small fixtures should use the tightest practical absolute/relative tolerance;
- tests may not use broad tolerances merely to hide implementation drift;
- NaN, infinity, missing, and unavailable states are asserted explicitly rather than being coerced to zero.

The tolerance policy itself must be versioned with the fixtures.

## UI rendering proof

After backend oracle PASS, browser QA must prove representative validated artifacts are displayed correctly.

For each analytical page with numeric results, machine-readable browser assertions must compare displayed values/plot payloads against the validated backend artifact, including at minimum:

- KPI values;
- table values;
- Plotly x/y coordinates for the principal analytical chart;
- units/percentage scaling;
- unavailable values;
- winner/final-weight values on Multivariate.

A screenshot is supporting visual evidence only. Screenshot similarity is not numerical validation.

Dash callbacks must not independently recalculate financial metrics merely to satisfy display assertions.

## Required evidence artifact

The gate must emit an immutable, sanitized `financial-numerical-validation-v1` evidence artifact containing at least:

- repository/application SHA;
- fixture version/fingerprint;
- algorithm-version identifiers under test;
- list of validated metric families;
- numerical tolerance policy version;
- pass/fail result for Univariate, Bivariate, Multivariate, OOS/leakage, and UI-artifact parity;
- no credentials, DSNs, market secrets, or raw production data.

## Failure policy

A mismatch between the independent oracle and Portfell is a production defect, even if existing regression tests pass.

The QA change must not silently alter the oracle to match production output. The discrepancy must first be classified as one of:

- production implementation defect;
- frozen contract/specification defect;
- oracle/test defect;
- numerical-tolerance defect.

Any change to a formula or financial convention requires an explicit versioned contract decision and corresponding updated oracle evidence. It must not be disguised as a visual, refactor, or regression update.

## Acceptance

The numerical gate is PASS only when all of the following are true:

- independent expected values are traceable from frozen inputs;
- Univariate contracted metrics pass the oracle;
- Bivariate contracted metrics pass the oracle;
- Multivariate portfolio arithmetic and OOS winner evidence pass the oracle;
- leakage checks pass;
- unavailable/missing values remain unavailable rather than plausible zero;
- backend persisted artifacts match independently derived values;
- browser-visible numerical values and Plotly payloads match those validated artifacts;
- the complete repository merge-quality gate passes;
- the immutable `financial-numerical-validation-v1` evidence artifact is produced.

Final production acceptance is blocked if this artifact is absent or FAIL.
